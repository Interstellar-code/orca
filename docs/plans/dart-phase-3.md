## Goal

Make the Dart tab feel like dartai: columns by status, dartboards and Orca's own saved views as places to look, subtasks nested, a card dragged between columns changes its status, blockers visible on held work, and the page refreshes on demand without losing the user's place.

Done when:

1. G1 — A List / Board switch in the Dart tab; the board shows one column per status with cards for the tasks; the choice is remembered.
2. G2 — The user picks a dartboard as the scope, and can save the current filters and layout as an Orca saved view, then pick, rename or delete it. Saved views are stored on the host per Dart account and follow a remote host (D2).
3. G3 — Every open task in the scope is on the board up to 1,000; finished columns show the 50 most recently completed with "Show 50 more"; past 1,000 the board says so (D3).
4. G4 — Subtasks appear nested under their parent in the list and in the detail, and are not repeated at the top level (D6).
5. G5 — Dragging a card to another column (or "Move to" from its menu) changes its status through phase 2's write queue, with the optimistic move, rollback, the unknown-outcome notice and the rate-limit message; no reorder inside a column, no move across dartboards (D5).
6. G6 — On hold is visible: a custom `On hold` status is its own column, an `on-hold` tag can be filtered with one chip, on-hold cards show "Blocked by N" / "Blocking N", and the detail shows blockers and lets the user add or remove "Blocked by" links (D7, D8).
7. G7 — Refresh happens on the refresh button and when the window becomes visible again; no polling timer; "Updated N ago" shows the age of the data; a refresh keeps scroll, selection, open menus and pending edits (D4).
8. G8 — Remote hosts, older hosts, the web client and folder workspaces behave; mobile still hides Dart; all repo gates pass.

Out of scope: reorder inside a column (`POST /tasks/{id}/move`), drag across dartboards, dartai's own saved views (`view`, `view_id`), polling, `updated_at_after`, "Blocking" edits, duplicate/related links, add subtask, multiple assignees, custom properties (phase 4), attachments, time tracking, delete, Docs, Dart on mobile.

## Decisions

1. D1 — Capabilities. Three new constants in `src/shared/dart/dart-capabilities.ts`, advertised next to the others: `dart.board.v1` (the new `ListTasks` keys `parentId`, `ids`, `order`; `offset` honoured; `getTask` returns `relationships`), `dart.savedViews.v1` (the two `ui.*Dart` saved-view methods), `dart.relationships.v1` (the blocker write method). The renderer probes them per target exactly as phase 2 does for `dart.writes.v2` (`DartApi` gets one method, `supportedDartFeatures(): Promise<DartHostFeatures>`, F3). Behaviour on a host without them: without `dart.board.v1` the board still pages open tasks to 1,000 and reads finished pages (F3: `offset`, `isCompleted` and `limit` exist on `dart.provider.v1` hosts), with no `order` key, so the finished section is labelled "50 finished tasks (not necessarily the latest). Update the remote Orca server for the latest." (a test with a fake old host returning older tasks first proves the label), and with no child reads, ids reads or blocker markers (rows already loaded still nest, D6); without `dart.savedViews.v1` the saved-view picker shows the update message (Jira's behaviour, item 9) and filters still work; without `dart.relationships.v1` blockers are read-only. Because `ListTasks` is strict ("What exists" item 1), sending a new key to an old host would be refused, so the renderer never sends one without the capability. One gate: B3 resolves the capability set once per target (`DartBoardFeatures`, frozen in B3.0) and every request builder takes it; no component checks capabilities itself. On a host without `dart.board.v1`: no `parentId`, `ids` or `order` key, no child, id or on-hold enrichment reads, and relationship state is `unsupported` (never shown as "no blockers"). On a host without `dart.relationships.v1`: no optimistic blocker change and nothing enqueued or sent. B3 tests each case by the requests the fake host records (none carrying a new key).
2. D2 — Orca saved views (Rohit, question 1). Dartai views are not used (no list exists in the API or the Dart MCP server). A saved view is `{ id, name, filters, layout, showEmptyColumns, nestSubtasks }`, where `filters` is the Dart tab's full filter state: `mine`, `status`, `dartboard`, `search`, plus phase 3's `tag`, `priority`, `onHold` and `blockedOnHold` (every control B5 adds to the filter bar must be in this set, so a view restores exactly what is on screen). Stored on the host in `PersistedUIState.dartSavedViewState` as `{ [dartUserId]: { views, activeViewId, updatedAt } }` with the account derived by the host (F6), so a view follows its remote host and two Dart accounts on one host do not share views. Limits copied from Jira: 50 views per account, 80-character unique names (case-insensitive), plus at most 20 account entries per host (oldest account by last write dropped first, never the current one). Selecting a view applies its filters and layout; changing a filter after that shows the view as modified ("Save" / "Save as new").
3. D3 — How much is read (Rohit, question 2). A board or list read is two parts. Open: `isCompleted: false`, pages of 250 with `offset`, up to 4 pages (1,000 tasks), stopping early when a page is short (`raw.rowCount` below the limit) or the total (`raw.totalCount`) is reached. Finished: `isCompleted: true`, `order: '-completed_at'`, 50 per read, "Show 50 more" reads the next 50 with `offset`. Offset paging has no snapshot: tasks changing in Dart during a read can shift rows between pages. So every cursor (`offset` and `doneOffset`) advances by `raw.rowCount` of the list reply, the rows Dart sent before the host dropped unmappable ones (not by the mapped or deduped count). A host that sends no `raw` is advanced by the mapped rows it returned (this can repeat a row, which dedupe removes, and never skips one); an empty page stops the read, and a short mapped page before the total marks the read set possibly incomplete (`partialReason: 'oldHost'`), because a dropped row cannot be told from the end of the data. A read set is marked possibly incomplete when a page is short before the total, ids repeat, or the final count differs from Dart's `count`; then the count line says "About N open tasks (Dart changed during the read) · Refresh" instead of a total. The finished part has its own cursor (`doneOffset`, raw rows) and a read generation: a refresh or any change of server filter (`dartboard`, `mine`, `search`, F4), scope, account or host starts a new read set, which resets `doneOffset` to 0 and bumps the generation, and a "Show 50 more" reply from an older read set (generation or cache key) is dropped. A client-filter change (`status`, `tag`, `priority`, `onHold`, `blockedOnHold`) starts no read set: it only projects the loaded rows, leaves `doneOffset`, the generation and the loaded finished pages unchanged, and a later "Show 50 more" reads the next unread page. Appended pages are deduped by id against what is shown. Dedupe is global across open and finished: when the same id comes back twice, the record with the newer `updatedAt` wins (ties: the later read), and the winner's `completedAt` decides only whether it counts as finished (F7); its status chooses the column (D9). Only one "Show 50 more" read runs at a time (the button is disabled while it runs). Offset paging has no snapshot, so a task deleted or reordered in Dart during a read can be missed; Orca does not hide this: such reads are flagged "possibly incomplete" as above, and the user's Refresh starts a new read set. The count line reads "N open of M · K latest done"; when open tasks exceed 1,000: "Showing 1,000 of M open tasks. Narrow the view." Each part's total comes from Dart's `count`. Pages are read one after another, never in parallel. Dedupe by id across pages (an item can move between pages if it changes during the read). Unverified: whether `is_completed` treats a Cancelled-kind status as completed (P3 check C2).
4. D4 — Refresh (Rohit, question 4). No timer. A refresh runs on the refresh button and when the document becomes visible again if `DartScopeMeta.fetchedAt` is older than 2 minutes (F8; the store's 60 s cache TTL does not drive this) (one read set, at most 5 reads). "Updated N ago" uses `DartScopeMeta.fetchedAt` (set only when a read set completes, F8) and `use-now`. Two different clocks, on purpose: the store's 60 s TTL only decides whether a re-mount may reuse the cache without reading; the 2-minute rule only decides whether returning to the window triggers a refresh. A refresh is quiet when rows exist: no skeleton, rows stay, scroll and selection stay, open menus and pickers stay, and phase 2's `withPendingDartPatches` re-applies pending edits over the incoming rows. `dart.rateLimited` (or any error) on any page stops the read set and discards that read set's pages: the previous complete read stays on screen unchanged (with its own `fetchedAt`) and the message shows; nothing retries. A first read (nothing on screen yet) shows the pages it got with `partialReason` and the message.
   4a. D4a — Phase 2 writes reach the board cache. `readDartScope` stores ONE ordinary `CacheEntry<DartTaskPage>` in `dartListCache` (`dart-slice-contract.ts:27-28`), key `scopedDartCacheKey(scope, 'scope::' + JSON.stringify(serverFilters))` (`DartServerFilters`, F4), registered as an alias like every list read: `data.tasks` is the single source of truth (open and finished rows together, deduped), `data.totalCount` the open total. The read metadata (`openTotal`, `doneTotal`, `doneOffset`, `generation`, `incomplete`, `partialReason`) lives in a separate `dartScopeMetaCache` keyed the same way and holds no task objects. `open` and `done` are never stored: B4's selectors rebuild them from `data.tasks` on every render (a task is "done" when `completedAt` is set). So phase 2's `patchDartTask` and `invalidateDartLists` cover the board with no new code in phase 2 files and no second copy to go stale.
