## Goal

Make the Dart tab do what the backend and the CLI already do: today the tab is read-only, while `src/main/dart/dart-tasks.ts` already creates, updates and comments, and `orca dart update` uses them.

Done when:

1. G1 — In the task detail, a user can add a comment and reply to a comment.
2. G2 — Status, priority and assignee are pickers in the task detail; choosing a value saves it.
3. G3 — Tags, size, start date, due date and title can be edited in the task detail.
4. G4 — A task can be moved to another dartboard from the detail view.
5. G5 — The description can be edited without overwriting changes made on dartai meanwhile (targeted patch, see "Decision D1").
6. G6 — A "New task" button in the tab creates a task.
7. G7 — Every write works on a remote host (runtime RPC path), not only local, and a host that is too old for a feature says so (or hides that control) instead of failing oddly or silently dropping the value.
8. G8 — Safety: the task is re-read after each save; edits show at once and roll back with a message if Dart refuses; a rate limit shows its message and is never retried silently; there is no delete anywhere.
9. G9 — All repo gates pass and the fork still merges upstream with small conflicts.

Out of scope (phase 2 and 3): reorder inside a column (`move_task`), multiple assignees, reviewers, custom properties, relationships and blockers, attachments, time tracking, delete, Docs, Dart on mobile (mobile hides Dart on purpose since commit `588b79f0984`; note only, no mobile work). Phase 3 (board, saved views, subtasks, drag, polling) is a separate plan.

## Decisions

1. D1 — Safe description edit, using Dart's targeted patch. The public API has it: `POST /tasks/{id}/update-description` (`operationId: updateTaskDescription`), body `{ "updates": [ { "type": "replace" | "insert_before" | "insert_after" | "delete", "oldText", "anchorText", "newText", "occurrence" } ] }` (1 or more updates, applied in order, each on the result of the previous one, atomically; "when occurrence is omitted, the target text must be unique"), reply `{ item: Task }`, 400 on invalid, 404 on unknown task. So the save sends only what the user changed; text edited on dartai elsewhere stays, and if the text the user changed was itself changed meanwhile, the `oldText` no longer matches and Dart refuses (400): that is the conflict signal. Fallbacks: (a) a description that was empty when editing began cannot be patched (`oldText` needs text): re-read the task right before save and only send a full `PUT` if the description is still empty, otherwise show the conflict dialog; (b) a host without the new capability keeps the description read-only with "Update the remote Orca server to edit descriptions"; (c) if the T0 spike shows that the markdown from `GET` is not the text the patch searches, the whole description save becomes re-read, compare, warn if changed, and a full `PUT` only when unchanged (never an overwrite of a changed description). Unverified until T0: everything above comes from the spec only.
2. D2 — Description editor is a plain markdown textarea with a preview, not the Linear rich editor. The rich editor (`LinearIssueMarkdownDescriptionEditor`) re-serializes markdown, so an untouched paragraph can come back different and would show up as a change in the diff. A textarea returns exactly the text typed, so the patch holds only real edits. Rich editing can follow later.
3. D3 — One write at a time per task (serialized), applied optimistically. Rollback goes to the last confirmed server state. A transport error or timeout on a write (not a clean `{ ok:false }`) is "outcome unknown": do not roll back blindly, re-read the task with `force` and show the server's truth with the message "Dart may have applied this change" (same idea as the CLI's `dart_write_unverified`, `src/cli/dart/dart-call.ts`).
4. D4 — Rate limit: `dart.rateLimited` (existing, `src/main/dart/dart-failure.ts:31-33`, message carries `Retry-After` when sent) rolls the edit back and shows the message in a toast. No automatic retry, no replay queue. No rate-limit header has ever been seen (#8, item 7.8), so the numbers are unknown.
5. D5 — One new capability, `dart.writes.v2` (constant `DART_WRITES_V2_RUNTIME_CAPABILITY` in `src/shared/dart/dart-capabilities.ts`), advertised next to `dart.provider.v1`. It stands for exactly the three things an old host cannot do: the `dart.updateTaskDescription` method, the `size` field, and `YYYY-MM-DD` date-only values. The other writes (status, priority, assignee, tags, title, dartboard, datetime dates, comments, create) already ship under `dart.provider.v1` and need no new gate. The renderer gates the description editor, the size control and the date inputs on it, and the write layer refuses to send `size` or a date-only value to a host without it (defence in depth: an old host would drop `size` silently). The Electron desktop's own host (`window.api.dart` = the IPC bridge `dart-bridge.ts`) always has it. Nothing else does by default: a remote environment target and the web client's paired host (`createWebDartApi`, which sends RPC to a host that may be older) must be probed. `DartApi` gets one extra method, `supportsWritesV2(): Promise<boolean>`, true in the desktop bridge and a capability probe in the web API (T1); the runtime client uses it for local targets and probes the capability itself for remote environment targets (T2). The new RPC method `dart.updateTaskDescription` has permission `workspace`, like the other writes.
6. D6 — Dates go on the wire as `YYYY-MM-DD` when the host has `dart.writes.v2`. The contract today (`dart-params.ts:160`) demands a datetime with offset, which the spec's "ISO format, like YYYY-MM-DD" does not require, so the new schema accepts both.
7. D7 — `size` is added to the create and update schemas (string, integer or null; values offered from `/config` `sizes`). The host does not validate it against `/config` (a size can be a number); Dart's 400 maps to `dart.badRequest`. The "at least one update" refine (`:190`) counts `size`.
8. D8 — No delete anywhere: no UI, no new RPC method, no CLI change. This is a review item, not a test: the reviewer checks the diff for any `DELETE` request, delete method name or delete control.
9. D9 — Moving to another dartboard sends `dartboard` through `dart.updateTask` (full-path title from `/config`, already validated by the host). The reply task is authoritative: if Dart changed the status because the target board has other statuses, the detail shows the new status.
10. D10 — Routing of models and efforts for these tasks is decided by the orchestrator at execution time (not in this plan). Builders never route.
11. D11 — List after a write. The list keeps the edited row on screen with its new values until the next refresh, even if it no longer matches the active filter (for example a status filter). After each successful write the store invalidates every `dartListCache` entry of the current scope (marks them stale, as the Jira patch action does with `fetchedAt: 0`), so the next list read refetches instead of serving a filtered page cached before the edit.
12. D12 — Text limits (the contract has none today and the Dart schema has no `maxLength` either, so these are Orca's own, chosen for the remote request cap in "What exists" item 9). New file `src/shared/dart/dart-text-limits.ts` with: `DART_TITLE_MAX_LENGTH = 500` and `DART_COMMENT_MAX_LENGTH = 50_000` (characters), and `DART_REQUEST_TEXT_MAX_BYTES = 256 * 1024` (UTF-8 bytes), measured with `measureUtf8ByteLength` from `src/shared/utf8-byte-limits.ts`. The byte cap applies to the full description in create and update, and to a description patch as the sum of the UTF-8 bytes of every `oldText`, `newText` and `anchorText` in the request (a small edit to a long description passes; only a big rewrite can hit it). The host schema in `dart-params.ts` enforces all three; `rpc-param-primitives.ts` is shared and is not edited. The renderer checks the same limits before sending (a pure `checkDartRequestText` in the same file) and shows a clear message (`translate`, for example "This text is too large to save to Dart from Orca ({{size}} KB, limit {{limit}} KB). Shorten it or edit it in Dart."). JSON escaping can inflate text (quotes, newlines and control characters take 2 to 6 bytes), so T2 also measures the serialized params of every write sent to a remote or web-paired host against `REMOTE_RUNTIME_MAX_INBOUND_REQUEST_JSON_BYTES` and refuses with the same kind of message instead of letting the socket close. A description already longer than the cap can still be read, and edited by patch as long as the changed text fits.

## Rules for every worker (copy into each worker prompt)

1. Only the main orchestrator routes. You never call `jev_*`, never pick or switch models, efforts or agents, and use your default model for any subagent your prompt allows.
2. Stay inside "Files owned". If you need a change in a file you do not own, stop and report it; do not edit it.
3. Never `git checkout` or `git stash` to undo; fix forward.
4. No silent workarounds. If the named tool, path or method fails, stop and report: what was called, the exact text, the likely cause. Ask before any substitute. A failed tool gets three real tries, each changing something.
5. Follow `AGENTS.md` and `docs/STYLEGUIDE.md`: shadcn primitives in `src/renderer/src/components/ui/`, tokens from `main.css`, comments only where code cannot say it (one line, why not how); no vague file names (`helpers`, `utils`); no type assertions except `as const` without a line-specific `SAFETY:` note; reuse before reimplementing; avoid low-value tests (`docs/agents-md-refs/test-antipatterns.md`: no list-membership or inventory tests).
6. First-class concerns on every change: macOS/Linux/Windows, remote hosts (mixed client and server versions), folder workspaces (a Dart task link must keep working for a plain folder), mobile (Dart stays hidden there; do not touch `mobile/`).
7. Run your task's checks and report the real output. Do not claim done without it.
8. Never print, log, commit or paste the Dart token. Do not write to the user's real Dart workspace; live write checks happen only in T0 and T8, on a throwaway dartboard the user names.
9. Every new user-facing string uses `translate('auto.components.task.page.dart.<File>.<key>', 'English default')` like the existing Dart files; new error codes also get an English `COPY` entry.
10. Copy patterns from the current files named in the task, not from memory.
11. Each task has its own fixture file (named in the task); do not edit another task's fixture file.

### T0. Spike: does the description patch work on real text (needs Rohit's go, live write)

Run by the orchestrator (or the user), not by a worker: workers never get the token. On a throwaway dartboard the user names, on one throwaway task (made in the Dart web app, or an existing one the user names), with the token read inside the command from the existing token file via a mode-600 header file and `curl -H @file` (never in argv, never `curl -v`):

1. `GET /tasks/{id}` and note the `description` markdown.
2. Pick one sentence in it. `POST /tasks/{id}/update-description` with a single `replace` of that sentence (`{"updates":[{"type":"replace","oldText":"<sentence>","newText":"<changed sentence>"}]}`).
3. `GET /tasks/{id}` again. Confirm: the changed sentence is there; the rest of the text is byte-for-byte the same (watch line endings, trailing whitespace, escaped characters, HTML entities, list markers); and that the `oldText` you copied from the `GET` output matched, which proves the `GET` markdown is the text the patch searches.
4. While there, record (no more writes than needed): the 400 body when `oldText` does not match; whether an empty `newText` is accepted for `replace` (otherwise the plan's `delete` is used); how `occurrence` counts when the text repeats; one `insert_after`; which format `dueAt` / `startAt` come back in after a `PUT` with `YYYY-MM-DD`; whether `size` round-trips as a string or integer.
5. Write the findings into the scratchpad first (ids and names scrubbed); the user reads them before they go into a `docs/` note (T8).

Accept: a short written result: "GET markdown equals patch text: yes/no", plus the observations in step 4. If "no" (or any surprise that makes a patch unsafe), D1 (c) applies: T6 builds the re-read, compare, warn flow with a full `PUT` only when unchanged, and drops the patch call. The orchestrator tells the T6 worker which branch to build.

## Risks

1. Upstream conflicts: the plan avoids editing Jira, Linear, GitHub and `Surface.tsx` files; the shared files touched are the RPC contract, the capability list, the failure-code union and its copy map, `api-types.ts`, and the generated catalog. Run `git merge-tree` against upstream `main` before the final merge to see the real conflict size.
2. Char-level diffs can produce many small updates for a heavily rewritten description; the builder falls back to one larger `replace` (the whole changed block) when the update count passes a small cap (tested).
3. Optimistic UI hides latency but a refused edit flips back; the message must name the field. The tests assert the message text, not only the rollback.
4. Date-only strings in a negative-offset time zone: covered by the timezone-safe formatter test (T4b step 5).
5. Not every description save is overwrite-proof. Only the patch path guarantees that nothing in Dart is overwritten (Dart refuses a patch whose `oldText` no longer matches). The empty-description path (T6 step 3a) and the D1 (c) fallback (if T0 shows the patch cannot be used) re-read the task and then send a full `PUT`: a change made in Dart between the re-read and the `PUT` (a window of well under a second to a few seconds) can be overwritten. The window is small, but it is not zero.
6. Pinned rows (D11) can show a task that no longer matches the filter until the next refresh; that is intended and the row clears on refresh or filter change.
