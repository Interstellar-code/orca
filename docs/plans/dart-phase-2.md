## Goal

Make the Dart tab do what the backend and the CLI already do: today the tab is read-only, while `src/main/dart/dart-tasks.ts` already creates, updates and comments, and `orca dart update` uses them.

Done when:

1. G1 — In the task detail, a user can add a comment and reply to a comment.
2. G2 — Status, priority and assignee are pickers in the task detail; choosing a value saves it.
3. G3 — Tags, size, start date, due date and title can be edited in the task detail.
4. G4 — A task can be moved to another dartboard from the detail view.
5. G5 — The description can be edited through Dart's targeted patch, which does not overwrite a concurrent change made in Dart, with one named exception (D1, "Accepted limit"). Orca reads the task again right before it sends the patch and sends nothing if the description changed. There is no full-description write for an existing task, and a description that cannot be patched uniquely is read-only in Orca.
6. G6 — A "New task" button in the tab creates a task.
7. G7 — Every write works on a remote host (runtime RPC path), not only local, and a host that is too old for a feature says so (or hides that control) instead of failing oddly or silently dropping the value.
8. G8 — Safety: the task is re-read after each save; edits show at once and roll back with a message if Dart refuses; a rate limit shows its message and is never retried silently; there is no delete anywhere.
9. G9 — All repo gates pass and the fork still merges upstream with small conflicts.

Out of scope (phase 2 and 3): reorder inside a column (`move_task`), multiple assignees, reviewers, custom properties, relationships and blockers, attachments, time tracking, delete, Docs, Dart on mobile (mobile hides Dart on purpose since commit `588b79f0984`; note only, no mobile work). Phase 3 (board, saved views, subtasks, drag, polling) is a separate plan.

The web client already reads a host's advertised capabilities with `getRemoteRuntimeStatus()` (`src/renderer/src/web/preload-api/web-runtime-calls.ts:199`) and `status.capabilities?.includes(capability)`, as `web-jira-filter-state-api.ts:23-37` does.

So a full `PUT` with `description` can never be made conditional, and the only conditional description write is `update-description`, whose `oldText` / `anchorText` must still match.

## Decisions

1. D1 — Safe description edit, and no overwrite path. Rohit's rule: a description edit in Orca must not overwrite a change made in Dart; the guarantee is the one stated under "Accepted limit" below, not an absolute one. Dart offers one conditional write, `POST /tasks/{id}/update-description` (`operationId: updateTaskDescription`), body `{ "updates": [ { "type": "replace" | "insert_before" | "insert_after" | "delete", "oldText", "anchorText", "newText" } ] }` (1 or more updates, applied in order, each on the result of the previous one, atomically; "when occurrence is omitted, the target text must be unique"), reply `{ item: Task }`, 400 on invalid, 404 on unknown task. Orca never sends `occurrence` (an ordinal match is not a stable identity: an identical paragraph added in Dart between our read and our write would redirect the edit with no conflict), so a non-unique target makes Dart refuse the request. The full `PUT /tasks/{id}` with `description` has no precondition ("What exists" item 13), so the app never sends `description` through `dart.updateTask` for an existing task: there is no unconditional description write anywhere in the UI. Consequences: (a) a description that was empty when editing began cannot be patched (`oldText` needs text), so it is read-only in Orca with a note, `Open in Dart` and `Copy`; (b) a host without `dart.writes.v2` keeps the description read-only with "Update the remote Orca server to edit descriptions" plus `Open in Dart` and `Copy`; (c) if Rohit's test shows that the markdown from `GET` is not the text the patch searches, every save would be refused (safe, nothing is overwritten) and a fix round hides the Edit button so the description stays read-only (`Copy`, `Open in Dart`); there is no `PUT` fallback; (d) a refused patch (400) is not proof of an external edit, because a malformed patch also gets a 400: the app reads the task again (forced, in the detail's scope) and opens the conflict dialog only when the fresh description differs from the text the edit started from; if it is the same, the editor stays open with the draft, a neutral persistent message ("Dart did not accept this change") and `Copy` / `Open in Dart`. Still creating a task sends its description (a new task has nothing to overwrite).
   Accepted limit (Rohit's decision, rounds 5 and 6: keep the targeted patch, add no read-only mode). Dart has no document revision, ETag or precondition on any write ("What exists" item 13), so Orca cannot make the patch conditional on the document it read. To narrow the gap Orca forces a fresh read in the detail's scope right before it sends the patch and sends nothing if the fresh description differs from the text the edit started from (T6 step 3). What remains: the patch can land on the wrong text only if, between Orca's pre-save read and Dart applying the patch, another edit replaces the exact text being changed and an identical copy of it exists elsewhere in the description. Every other concurrent change is handled: a change to the same text with no identical copy makes Dart refuse the patch; an identical copy with no replacement makes Dart refuse (not unique); edits elsewhere merge with ours. Unverified until Rohit's test: everything above comes from the spec only.

2. D2 — Description editor is a plain markdown textarea with a preview, not the Linear rich editor. The rich editor (`LinearIssueMarkdownDescriptionEditor`) re-serializes markdown, so an untouched paragraph can come back different and would show up as a change in the diff. A textarea returns exactly the text typed, so the patch holds only real edits. Rich editing can follow later.
3. D3 — One write at a time per task (serialized), applied optimistically; rollback goes to the last confirmed server state, but only when the write certainly did not apply. Outcome certainty is carried end to end ("What exists" item 11): the host puts `outcome: 'notApplied' | 'unknown'` on every failed write reply (T1); `notApplied` only when Dart answered with a 4xx status other than 408 (400, 401, 403, 404, 422, 429) or when the host failed before it sent the write (not connected, unknown name from `validateNamedFields`, a `/config` read failure before the write); everything else is `unknown`: network, timeout, HTTP 408, an unreadable 2xx body, 5xx, and any non-Dart error. The renderer's runtime client adds the same field for failures it detects itself (T2): a refusal before sending (capability, request size) is `notApplied`; an exception from IPC, RPC or the web call after the request left is `unknown`. Replies from an older host that carry no `outcome` are classified conservatively: `dart.updateFailed`, `dart.createFailed` and `dart.commentFailed` count as `unknown`; `dart.badRequest`, `dart.unauthorized`, `dart.rateLimited`, `dart.taskNotFound`, `dart.notConnected` and `dart.descriptionPatchRefused` count as `notApplied`. On `unknown` the state stays unreconciled until the user reconciles it, and nothing claims finality. Nothing rolls back blindly. The queue re-reads the task once with `force` as evidence, shows what that read returned labelled with the time of the read, keeps the optimistic marker on the affected field, keeps the draft, and shows a persistent notice: "Dart may have applied this change. Showing what Dart had when Orca last checked." with `Check again` (another forced read) and `Dismiss`. A read is evidence, not proof: a delayed write can land after it, so the notice never clears by itself, and a failed read leaves notice and draft untouched. While a field has an unreconciled unknown write, Orca sends no further write to that field (the control is disabled with the notice's hint) and never resends a comment or a create blindly (T5, T7); writes to other fields of the task stay allowed. The CLI's `dart_write_unverified` (`src/cli/dart/dart-call.ts`) is the same idea.
4. D4 — Rate limit: `dart.rateLimited` (existing, `src/main/dart/dart-failure.ts:31-33`, message carries `Retry-After` when sent) rolls the edit back and shows the message in a toast. No automatic retry, no replay queue. No rate-limit header has ever been seen (#8, item 7.8), so the numbers are unknown.
5. D5 — One new capability, `dart.writes.v2` (constant `DART_WRITES_V2_RUNTIME_CAPABILITY` in `src/shared/dart/dart-capabilities.ts`), advertised next to `dart.provider.v1`. It stands for exactly the three things an old host cannot do: the `dart.updateTaskDescription` method, the `size` field, and `YYYY-MM-DD` date-only values. The other writes (status, priority, assignee, tags, title, dartboard, datetime dates, comments, create) already ship under `dart.provider.v1` and need no new gate. The renderer gates the description editor, the size control and the date inputs on it, and the write layer refuses to send `size` or a date-only value to a host without it (defence in depth: an old host would drop `size` silently). The Electron desktop's own host (`window.api.dart` = the IPC bridge `dart-bridge.ts`) always has it. Nothing else does by default: a remote environment target and the web client's paired host (`createWebDartApi`, which sends RPC to a host that may be older) must be probed. `DartApi` gets one extra method, `supportsWritesV2(): Promise<boolean>`, true in the desktop bridge and a capability probe in the web API (T1); the runtime client uses it for local targets and probes the capability itself for remote environment targets (T2). The new RPC method `dart.updateTaskDescription` has permission `workspace`, like the other writes.
6. D6 — Dates go on the wire as `YYYY-MM-DD` when the host has `dart.writes.v2`. The contract today (`dart-params.ts:160`) demands a datetime with offset, which the spec's "ISO format, like YYYY-MM-DD" does not require, so the new schema accepts both.
7. D7 — `size` is added to the create and update schemas (string, integer or null; values offered from `/config` `sizes`). The host does not validate it against `/config` (a size can be a number); Dart's 400 maps to `dart.badRequest`. The "at least one update" refine (`:190`) counts `size`.
8. D8 — No delete anywhere: no UI, no new RPC method, no CLI change. This is a review item, not a test: the reviewer checks the diff for any `DELETE` request, delete method name or delete control.
9. D9 — Moving to another dartboard sends `dartboard` through `dart.updateTask` (full-path title from `/config`, already validated by the host). The reply task is authoritative: if Dart changed the status because the target board has other statuses, the detail shows the new status.
10. D10 — Routes (set by Rohit, 2026-11-04; use exactly these, add no other agents): T1, T2, T4a, T4b, T8 → Claude Code, Sonnet, medium. T3a, T3b, T6 → Claude Code, Opus, medium. T5, T7 → OMP, `9router-cloud/auto`, effort auto (`--thinking=auto`). Every review → Claude Code, Opus, medium. If an OMP lane stalls or returns empty answers, ask Rohit before moving it. Builders never route.
11. D11 — List after a write. The list keeps the edited row on screen with its new values until the next refresh, even if it no longer matches the active filter (for example a status filter). After each successful write the store marks stale every `dartListCache` entry that belongs to the same host and account as the write, whatever alias key it is stored under (the default-scope key the list uses and the explicit-scope key the detail uses are different strings, "What exists" item 6; T3 "mutation identity"), so the next list read refetches instead of serving a page cached before the edit. Entries of another host or account are never touched.
12. D12 — Text limits (the contract has none today and the Dart schema has no `maxLength` either, so these are Orca's own, chosen for the remote request cap in "What exists" items 9 and 12). New file `src/shared/dart/dart-text-limits.ts` with: `DART_TITLE_MAX_LENGTH = 500` and `DART_COMMENT_MAX_LENGTH = 50_000` (characters), `DART_REQUEST_TEXT_MAX_BYTES = 256 * 1024` (UTF-8 bytes, measured with `measureUtf8ByteLength` from `src/shared/utf8-byte-limits.ts`). The byte cap applies to the full description in create, and to a description patch as the sum of the UTF-8 bytes of every `oldText`, `newText` and `anchorText` in the request (a small edit to a long description passes; only a big rewrite can hit it). The host schema in `dart-params.ts` enforces the three text limits; `rpc-param-primitives.ts` is shared and is not edited. The renderer checks the same limits before sending (a pure `checkDartRequestText` in the same file) and shows a clear message (`translate`, for example "This text is too large to save to Dart from Orca ({{size}} KB, limit {{limit}} KB). Shorten it or edit it in Dart."). JSON escaping can inflate text and the host's cap counts the whole request envelope (`id`, `deviceToken`, `method`, `params`, orchestration fields), so the limit is enforced on the real serialized request where it is built, not estimated: T2 edits `serializeRemoteRuntimeRpcRequest` (`src/shared/remote-runtime/remote-runtime-memory-limits.ts:72-90`, its one named shared-file exception) so that a serialized request over `REMOTE_RUNTIME_MAX_INBOUND_REQUEST_JSON_BYTES` is refused before it is sent, with a `RemoteRuntimeClientError('invalid_argument')`, instead of the host closing the socket (1009). There is no placeholder token, no fixed reserve. A description already longer than the cap can still be read, and edited by patch as long as the changed text fits.
13. D13 — Drafts. Unsaved text (comment boxes, description edits, the new-task dialog) is kept in memory only, never on disk, keyed by host, account and task, and is never lost silently. Switching the active host deletes nothing: drafts stay under their own host key and are there when the user switches back. A clean entry (nothing typed, or equal to what is saved) may be evicted past 20 entries; a dirty draft is never evicted without the user: when a 21st dirty draft would be created, `setDraft` returns `full` and the editor shows an inline warning offering `Copy` of the oldest dirty draft and `Discard it`; the new draft starts only after that. Disconnecting Dart with dirty drafts asks first ("You have N unsaved Dart drafts": `Copy all`, `Discard and disconnect`, `Cancel`). The description close guard (T6) stays. 1. `dart-description-patch.ts`: `buildDescriptionUpdates(base, draft)` returns `{ kind: 'patch', updates }` or `{ kind: 'refused', reason: 'empty-base' | 'non-unique-anchor' | 'too-large' }`. It uses the `diff` package on `base` (the description when editing began) and `draft`. Dart applies the updates in order and each one searches the text as it stands after the previous ones, so the builder works from the end of the text toward the start: the last changed region first, the first one last, and checks uniqueness against the document as it stands at that step (base with the already-built later edits applied). For each changed region: pure removal gives `delete` with `oldText`; pure addition gives `insert_after` (anchor is the unchanged text just before) or `insert_before` (anchor is the text just after, when the region is at the start); a change gives `replace`. Each `oldText` or `anchorText` is widened with neighbouring unchanged text until it occurs exactly once in the current document. There is no `occurrence`: if no widening makes the text unique, the result is `refused` / `non-unique-anchor` and nothing is sent. If `base` is empty the result is `refused` / `empty-base` (the editor is not offered then, step 2). Past a small number of updates the builder collapses them into one `replace` of the whole changed block, which must also be unique, else `refused`. Over `DART_REQUEST_TEXT_MAX_BYTES` is `refused` / `too-large`.

4. Conflict dialog and recovery (`dart-description-rebase.ts`). The draft store keeps one lineage per description: (`base`, `draft`, `unresolved`) where `base` is the Dart text the edit started from, `draft` is the current editor text, updated as the user types, and `unresolved` is the list of the user's hunks that could not be applied (each `{ id, baseText, userText }`). `rebaseDraft(base, draft, latest)` returns `{ merged, unresolved }`: for each hunk of `base → draft`, locate its `base`-side text (the removed or replaced text plus its neighbouring context) in `latest`; if it occurs exactly once, apply the hunk to `latest`; otherwise (absent, appears twice, or the neighbouring text changed) the hunk is unresolved and is never applied automatically. Text in `latest` that is not part of any hunk (the remote additions) is kept as it is. "Back to editing" replaces the lineage with (`latest`, `merged`, the new `unresolved` hunks added to those already stored): the latest Dart text becomes the new `base`, the merged text the new editor text. Whatever the user types or resolves by hand afterwards is part of that draft. ## Risks

1. Upstream conflicts: the plan avoids editing Jira, Linear, GitHub and `Surface.tsx` files; the shared files touched are the RPC contract, the capability list, the failure-code union and its copy map, `api-types.ts`, and the generated catalog. Run `git merge-tree` against upstream `main` before the final merge to see the real conflict size.
2. Char-level diffs can produce many small updates for a heavily rewritten description; the builder falls back to one larger `replace` (the whole changed block) when the update count passes a small cap (tested).
3. Optimistic UI hides latency but a refused edit flips back; the message must name the field. The tests assert the message text, not only the rollback.
4. Date-only strings in a negative-offset time zone: covered by the timezone-safe formatter test (T4b step 5).
5. No full-description write path exists, but one race stays by decision (Rohit, rounds 5 and 6, D1 "Accepted limit"). Descriptions of existing tasks change only through `update-description`, which Dart applies only if the exact `oldText` / `anchorText` is still there and unique; there is no full-`PUT` fallback (the schema has no precondition, "What exists" item 13). Right before sending, Orca forces a fresh read and sends nothing if the description changed. The accepted, known limit: the patch can land on the wrong text only if, between Orca's pre-save read and Dart applying the patch, another edit replaces the exact text being changed and an identical copy of it exists elsewhere in the description. Orca cannot detect this because Dart gives no revision or precondition, and adds no read-only mode for it. What else remains by design: an edit in Dart that does not touch the text we patch merges silently with ours (non-overlapping edits are the point of a patch). Cost: an empty description cannot be filled from Orca, and a description Orca cannot patch uniquely is edited in Dart (`Open in Dart`).
6. Pinned rows (D11) can show a task that no longer matches the filter until the next refresh; that is intended and the row clears on refresh or filter change.
7. T2 changes one shared transport function (`serializeRemoteRuntimeRpcRequest`, six lines of admission check) that every remote RPC uses. It only refuses requests the host would already reject by closing the socket, but it is a shared-file edit that could conflict upstream: keep it minimal and covered by its own edge test.
